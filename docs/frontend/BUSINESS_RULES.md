# Business Rules

The rules a frontend needs to know to build correct UI, not just correct API calls. Anything here that contradicts intuition (or the old SpinBoard product) is called out explicitly.

## The billboard never stops and is never gated

- The billboard plays brand banner ads back-to-back — each a static image shown for a fixed 15 seconds (`Config: billboard.bannerDisplaySeconds`), not a video. Brands used to upload video; that switched to a banner image to cut hosting costs (see MIGRATION_NOTES.md) — every campaign, both tiers, uploads a banner now. There is **no quiz, no "watch 5 to unlock a spin," no try-again economy**. Watching is not a means to an end — it's the whole first-class experience.
- Nobody has to be logged in, or have a complete profile, to watch. Auth/profile-completeness only matter the moment someone tries to **claim** a code.
- Every viewer, everywhere, draws from the identical eligible ad pool. **There is no geographic or demographic targeting anywhere in the system** — not in ad selection, not in freebie code eligibility. If a future request asks for "show this ad only in Nigeria," that's a product reversal of an explicit decision, not a missing feature.
- A campaign enters the ad pool once it is **both** `status: "ACTIVE"` **and** `moderationStatus: "APPROVED"`, **and** it has a `bannerImageUrl` set — but there is **no pre-payment review gate**: a campaign auto-flips to `ACTIVE` + `APPROVED` the instant payment succeeds, so a paid campaign goes live immediately, unmoderated. Moderation is reactive: an admin who spots an inappropriate live banner pulls it (individually or in bulk) via `POST /ad-campaigns/deactivate`, which sets it back to `PAUSED` + `REJECTED`. `POST /ad-campaigns/reactivate` undoes that, as long as the campaign's original `expiresAt` hasn't since passed. Don't build a "pending review" waiting state into the brand dashboard between payment and going live — there isn't one.
- A brand can also self-serve pause their own live campaign (`POST /ad-campaigns/:campaignId/pause`) and resume it later (`POST /ad-campaigns/:campaignId/resume`) — no penalty, no strike, and this leaves `moderationStatus` at `APPROVED` so it's visibly distinct from an admin takedown (`moderationStatus: "REJECTED"`). A campaign an admin took down can **only** be brought back by the admin's own `POST /ad-campaigns/reactivate` — a brand's self-resume call on that campaign returns `403 ADMIN_TAKEDOWN`. **There is no refund of any kind on any takedown or pause, ever** — don't build refund UI or copy anywhere for this.
- Premium campaigns are picked ~2x as often as Basic (`Config: campaign.tiers.*.weight`), and never repeat back-to-back or within the last 5 slots served in a session.
- If the eligible pool is ever empty, a house-filler slot plays instead (`type: "HOUSE"` in the queue) — the stream is never empty.
- A live freebie code isn't only a small pin in the perimeter strip — it also takes over one billboard slot full-screen (`type: "FREEBIE"`), for the same fixed duration as a real ad (`Config: freebie.billboardSlotSeconds`, default 15s), exactly once per viewing session per code. This is deliberate: the anticipation of a freebie interrupting the ad reel is meant to keep people watching. It's additive, not a replacement — the code stays pinned in the strip for its whole live window regardless of whether/when it also took over someone's billboard. **This mechanic is entirely unchanged by the video→banner revamp above.** See `UI_CONTRACT.md` for the full playback contract.
- `GET /billboard/stats` (public) surfaces `watchingNow`/`codesToday`/`adsInRotation` for the watch screen's headline numbers. `GET /billboard/my-streak` (auth required) reports a viewer's consecutive-day watch streak: consecutive calendar days (platform timezone) with at least one completed, non-house-filler, non-freebie-slot view, counted backward from today-or-yesterday. It does **not** reset to 0 just because today has no completed view yet — only an actual gap day breaks it, so a viewer checking in the morning still sees yesterday's run reflected.
- A separate, admin-curated **sponsored ad panel** sits alongside the main billboard (`sponsoredAd` field on `GET /billboard/queue`) — not a brand self-serve product. Any advertiser (on the platform or not) can either negotiate a deal off-platform and have an admin upload the already-agreed creative directly (goes live immediately), or submit their own creative + contact details via the public `POST /sponsored-ads/submit` (lands `PENDING`, invisible on the billboard, until an admin reviews/negotiates and activates it — a real submission/review queue, `GET /admin/sponsored-ads?status=PENDING`). Either way, only an image or GIF, never video/audio. It's `null` on the billboard until something is `ACTIVE`. Freebie codes never appear in this slot. See `UI_CONTRACT.md`'s "Sponsored ad panel" section.

## AD slots can carry a clickable website link

- An `"AD"` slot's `clickUrl` (see `DATA_MODELS.md`) is resolved server-side as `campaign.campaignUrl || campaign.brandUrl || null` — a campaign-specific landing page always wins over the brand's general site when both are set. `HOUSE` and `FREEBIE` slots never have one; there's no campaign to click through to.
- Both `brandUrl` and `campaignUrl` must be a well-formed `http`/`https` URL when a brand sets them at `POST /ad-campaigns` — anything else (`javascript:`, `data:`, a relative path, malformed input) is rejected with `400` at creation time. This was previously unvalidated; don't assume old data is clean if you're reading it from anywhere other than a freshly-created campaign.
- Navigate on click **immediately**, using the `clickUrl` already in hand from the queue response — don't wait on `POST /billboard/impressions/click` before opening the link. That call is fire-and-forget tracking only, same pattern as the existing heartbeat/complete calls, and it's idempotent (a duplicate click on the same slot is silently accepted, not an error, and doesn't double-count).
- Click-throughs feed a brand's Premium-only analytics (`clicks`, `clickThroughRate`) — see "Premium-only analytics" above.

## Freebie codes: first to type wins

- A code shown `PINNED` in the strip is either currently **claimable** (`state: "AVAILABLE"`) or was **just claimed by someone** and is shown red for a short grace window (`state: "TAKEN"`) before it disappears — never shown as "coming soon." **The exact drop schedule is never exposed through any endpoint** — no exact time, no type, no id anything could be looked up by, so don't build a precise countdown timer; that data doesn't exist by design (unpredictability is the point). The one narrow, deliberate exception: `GET /freebies/next-drop-window` (see `API_GUIDE.md`) hands back a coarse, fixed 1-hour window (e.g. "8-9am") for the *next* drop only, with no type and no exact instant — enough for a "check back around..." hint, not enough to time a claim.
- Claiming is a race: the first authenticated, eligible submission of a live `publicCode` wins it; everyone else gets `CODE_ALREADY_TAKEN` (409). This is enforced atomically server-side — the frontend doesn't need optimistic locking, just handle the 409 gracefully (it will be common and is not an error state to alarm the user over).
- **Auth is required to claim, never to watch.** An unauthenticated submission is rejected with 401 and **changes nothing** — the code stays available for the next (authenticated) submission, including the same person trying again a second later after logging in.
- Claiming further requires: verified email + a complete profile (age, sex, country, state, city). `country` here is **only** collected for records/reporting — it never restricts who can see or claim anything.
- Claim limits are **per user, rolling 24h** (`Config: freebie.dailyClaimCap`, default 1/day — cash-only now, see below, so only the `CASH` bucket of this config can ever be hit). On hitting the cap: 403 `DAILY_LIMIT_REACHED` with `{type, resetsAt}` in `details` so the UI can say precisely when it resets.
- **Cash-only.** Airtime freebie codes are discontinued (unreliable carrier/network PIN delivery was discouraging users) — every freebie code drop is cash now, in varying denominations (₦50, ₦100, ₦200, ₦500, ₦1000, ...; whatever an admin has stocked). Winning a code always credits the wallet on redemption, never reveals a PIN. `type: "AIRTIME"` can still appear on a **pre-existing** claim in `GET /me/claims` for anyone who won airtime before the cutover — build the claims-history UI to still render that case correctly (PIN reveal on redeem), but don't build any *new* UI (a type selector, an "airtime vs cash" choice) around it — no new code will ever be `AIRTIME`.
- Winning a code issues a **secret code** immediately in the claim response — this is the only time it's shown in full in a claim response; after that it's only visible via `GET /me/claims`.

## Redeeming: separate step, separate endpoint semantics, same button

- Applying a secret code is what actually pays out — credits the wallet (every code is cash now; a recharge-PIN reveal can still happen, but only for a pre-cutover `AIRTIME` claim someone won before the cash-only switch). It is a **deliberately separate step** from claiming, but the frontend can and should offer **one input box and one Apply button** for both: `POST /freebies/apply` auto-detects whether the submitted value is a live public code (→ claim) or one of the caller's own secret codes (→ redeem).
- Redeeming the same secret code multiple times is **safe and idempotent** — it credits the wallet (or reveals the PIN) exactly once, and every subsequent call returns the same result (current wallet balance / the same PIN) rather than an error or a duplicate credit. Build the UI accordingly: re-submitting after a network hiccup is not dangerous and doesn't need a confirmation dialog.
- A secret code submitted by someone other than the account that won it is rejected as `CODE_INVALID` (404) — **identical** to a code that simply doesn't exist. The response never distinguishes "not real" from "not yours," so don't build UI that tries to tell a user their friend's leaked code belongs to someone else.
- Redemption has its own, tighter rate limit than claiming (`Config: rateLimit.redeem`, default 5/min) since it's the money-creating operation — a burst of legitimate retries (e.g. a flaky connection) can plausibly hit this; handle 429 (`code: "TOO_MANY_ATTEMPTS"`) with a "slow down and try again" message, not a hard failure state.

## Nothing a user has won ever expires

This is a hard, load-bearing rule across the whole product, not just freebie codes:
- A claimed freebie code's secret code can be redeemed any time — a day, a week, or a year later. There is no deadline field anywhere on `Claim`.
- The only "expiry-shaped" thing in the whole freebie system is `liveUntil` on an **unclaimed** `FreebieCode` — that's a display-rotation timer for something nobody has won yet, conceptually unrelated to an expiry on something a user has won. Once a code is claimed, `liveUntil` stops mattering entirely.
- Don't build a "your reward expires in X days" banner anywhere. If a design calls for one, that's a rule change, not a missing feature.

## Wallet cash only ever leaves the platform through a manual weekly run

- There is **no withdrawal or transfer endpoint** anywhere in the API. A user cannot self-serve a cash-out. Don't build a "Withdraw" button that hits an endpoint — it doesn't exist, on purpose.
- `GET /wallet/balance` surfaces `payoutThreshold`, `amountToThreshold`, and `nextPayoutDate` so the frontend can show progress toward the next payout ("₦350 more to reach this Friday's payout") without needing to know how the run itself works.
- Being below `payoutThreshold` only excludes a user from a payout *run* — it never restricts anything else, since there is nothing else in the product that spends wallet balance (the marketplace has no checkout at all — see below).
- Bank account details (`POST /wallet/bank-accounts`) are still collected and Paystack-verified — they now feed the manual payout export instead of an automated transfer.

## The marketplace is a directory, not a store

- There is **no checkout, no price paid in-app, no order, and no discount code anywhere in the marketplace.** `POST /marketplace/checkout`, `GET /marketplace/orders/*`, and the entire `DiscountCode` concept have been removed, not just hidden — don't build a cart, a checkout flow, or a discount-code input anywhere in the marketplace UI.
- A brand publishes a **business profile** (name, description, logo, contact email/phone/WhatsApp, address, social links) and, optionally, a set of **showcase products/services** (name, description, photos, an optional free-text `priceLabel` like `"From ₦5,000"` or `"Contact for quote"` — never a real charged amount). A user browses the directory, opens a business or a specific product, and contacts the business directly using the info shown — there is no in-app messaging or purchase action to build either, just clear, tappable contact links (`tel:`, `mailto:`, `https://wa.me/`, social profile links).
- A business only appears anywhere public once the brand explicitly sets `isListed: true` — this is never automatic just because the profile fields are filled in. Publishing requires at minimum a name and one contact method (email, phone, or WhatsApp); attempting to publish without them returns `403 PROFILE_NOT_LISTABLE` (`code`, not just a message — check DAILY_LIMIT_REACHED-style structured errors elsewhere for the pattern).
- Unpublishing a business (`isListed: false`) hides its products from every public browse/search/detail endpoint too, in one move — the frontend doesn't need to separately deactivate each product when a brand takes their listing down.

**The referral feature has been removed entirely** — `/referrals/*`, referral capture at signup (`referrerId`/`referrerUsername`/`referralCode` in registration bodies), referral stats on the viewer profile response, and the `referralBonusAlerts` notification toggle are all gone. Don't build or port any referral UI (invite links, "your referrals" dashboard, referral milestone rewards).

## Suspicion scoring flags, it never blocks

A claim can be flagged `suspicious: true` (visible only in the admin claims view, never to the claiming user) for signals like inhuman latency between a code going live and being claimed, a headless-browser user agent, or no prior poll of the strip feed from that IP. **A flagged claim still succeeds normally for the end user** — this is a review signal for admins, not a gate. Don't build any end-user-facing "your claim looked suspicious" messaging; it doesn't exist and shouldn't.

## Premium-only analytics

Ad campaign analytics (`GET /ad-campaigns/:id/analytics*`) return 403 for Basic-tier campaigns — this is a monetization gate, not a bug. Build the brand dashboard to show an upsell/upgrade prompt for Basic campaigns rather than an empty chart. The analytics response also carries `costPerCompletedView` (nullable), `uniqueViewers`, and `clicks`/`clickThroughRate` (website-link click-throughs, see "AD slots can carry a clickable website link" above) — all real fields, not placeholders.

## Ad moderation is reactive, and escalates: report → auto-flag → warn/takedown (strike) → auto-suspend

A companion to "the billboard never stops" above — this is what admins do about a live banner ad that shouldn't be, after the fact:

- Any signed-in caller can report a running campaign (`POST /ad-campaigns/:campaignId/report`, `{ reason }`) — one report per user per campaign; a repeat report from the same user is silently accepted as a no-op (`reported: false`), not an error, since their signal is already on record.
- Enough reports in a short window (`Config: adModeration.autoFlagReportThreshold` reports within `adModeration.autoFlagWindowMinutes`, defaults 3 within 60) auto-flags the campaign (`AdCampaign.flagged: true`). **Flagging never takes a campaign down by itself** — it's purely a signal surfaced to the admin monitor screen (report counts, flag badges); the ad keeps airing until an admin acts.
- An admin has two responses, both of which add a **strike** to the brand: `POST /ad-campaigns/:campaignId/warn` (campaign stays live, lighter response, clears the flag) or `POST /ad-campaigns/deactivate` (campaign pulled — see the pause/resume section above, `reason` required, no refund).
- Once a brand's strike count reaches `Config: adModeration.suspendStrikeThreshold` (default 3), they're **automatically suspended** — same effect as an admin calling `POST /admin/brands/:brandId/suspend` directly (which also exists for an immediate, no-strikes-required suspension on a severe violation). Suspension immediately pauses every `ACTIVE` campaign the brand has running, and blocks new campaign creation, going live, self-resuming a campaign, and creating a Promote & Earn campaign (`403 BRAND_SUSPENDED` on each).
- `POST /admin/brands/:brandId/unsuspend` lifts a suspension but does **not** reset the strike counter or reactivate campaigns that were paused by it — those need individual `POST /ad-campaigns/reactivate` calls.
- Nothing here sends an email or notification to the brand at this point — a warn or suspend is only visible by the brand checking `GET /profile/brand` (which now surfaces their own `strikeCount`/`suspended`/`suspendedReason`) or the admin dashboard. Don't build a "you've been warned" toast/email expectation — there's no push for it yet.

## Promote & Earn: one grand prize, decided by a promoter's likes summed across every campaign they've shared

- A brand posts a `PromoCampaign` for free — no payment, no pre-publish moderation queue, auto-`ACTIVE` on creation (same posture as ad campaigns). A viewer mints a personal share link per campaign and posts it externally; anyone who follows that link back and likes/votes there (signed in) adds to that promoter's running total.
- **There is no per-campaign prize or per-campaign leaderboard.** A promoter's score is the sum of their non-voided likes across *every* campaign they've shared, within the current admin-opened prize period — see `GET /promote/leaderboard`'s `entries[].likeCount`. Sharing more campaigns is a real strategy for raising a promoter's odds, since every campaign's likes feed the one running total. Don't build a "this campaign's top sharer" view as anything other than a curiosity stat — it's not what wins the prize.
- **Prize periods (`PromoPrizePeriod`) are opened and settled automatically, weekly, by default.** A daily job (`services/scheduler/index.ts runWeeklyPromoPeriodMaintenance`) settles any `OPEN` period whose `periodEnd` has passed — crediting the winner's wallet exactly as a manual settle would — and opens this week's period (Mon 00:00 → next Mon 00:00, platform timezone) if one doesn't already exist for that exact week, using a Config-driven default prize (`Config: promote.autoPeriod.prizeDescription` = "Weekly Promote & Earn cash prize", `Config: promote.autoPeriod.prizeAmountNgn` = ₦10,000). `Config: promote.autoPeriod.enabled` (default `true`) is a kill switch. Auto-opened/auto-settled periods carry `createdBy`/`settledBy: "system"` rather than a real admin id. **An admin can still open/settle/cancel a period manually at any time** via `POST /admin/promote/periods` / `.../settle` / `.../cancel` — e.g. to run a one-off prize with a different amount or description for a particular week; the automatic weekly period only fires if nothing has already claimed that week's start date, it isn't a hard override of manual action. `GET /promote/leaderboard` with no `periodId` shows the currently `OPEN` period; if none is open (a rare gap, only right after a settle and before the next daily tick opens the new one), it returns `period: null` and an empty `entries` array — that's a normal state to design for, not an error.
- **No account-age gate on liking/voting** — a brand-new account can vote immediately after registering. The gate that exists instead: **one vote per user per (promoter, campaign) pair.** This is a brand-awareness contest: a liker can vote for as many different promoters as they want (Mr. A, Mr. C, Mr. D, ...), each an independent vote — and separately, for each distinct campaign a given promoter shares (Mr. A's 1st campaign and Mr. A's 2nd campaign are two independent, both-countable votes toward Mr. A's total). The only thing blocked is voting for the exact same promoter+campaign pair twice — submitting that returns `alreadyLiked: true` and `message: "You have already voted for this promoter on this campaign."` — a normal `200`, not an error, so don't show a failure state, show that message.
- A promoter can't like their own share link (`400 SELF_LIKE_NOT_ALLOWED`) — the one self-farming vector closed outright rather than just rate-limited.
- Settling a period credits the winner's wallet directly (`WalletTransaction.reason: "PROMOTE_GRAND_PRIZE"`) only if the period carries a cash `prizeAmount`; a period can also carry a non-cash prize description with no `prizeAmount`, in which case settling just records the winner and the admin fulfills the prize manually outside the system.
- Fraud response is reactive, same posture as ad-campaign moderation: an admin can void a specific like or disqualify a promoter outright (globally, not per-period) after the fact — there's no upfront review gate on either campaigns or likes.
- **The full funnel is tracked, not just likes**: click (a visitor follows the share link) → signup (they create an account) → like (they like the campaign). `GET /promote/l/:slug` is the landing-page endpoint — call it whenever a visitor arrives via a share link, and it logs the click automatically; there's nothing else to wire up for the click stage. Signup attribution needs **no code/referrer field for the visitor to enter** — it rides the same anonymous-session cookie the billboard flow already uses for logged-out viewers, so whichever share link they most recently followed gets credited the moment they register (last-touch: if they followed more than one promoter's link before signing up, the most recent one wins). `clickCount`/`signupCount` appear on `GET /promote/links/mine` (a promoter's own funnel) and on the brand/admin campaign views (`GET /promote/campaigns/mine`, `GET /promote/campaigns`) — deliberately **not** on the public `GET /promote/campaigns/:campaignId` detail read, which stays `likeCount`-only.

## Business KYC: automated pre-check, but a human always decides

- KYC exists to gate the B2B marketplace below — real contracts and money move through it, so a business must be `kycStatus: "verified"` before it can post a Project or submit a Quotation.
- Submitting (`POST /kyc/submit`) runs an automated CAC (Corporate Affairs Commission) lookup as a fast fraud pre-filter, but **the result never auto-approves anything** — every submission lands on `pending_review` regardless of how clean the automated match was, and only an explicit admin `POST /admin/kyc/:id/approve` moves it to `verified`. Don't build a "you're verified!" success state right after submission — the real state is "submitted, awaiting review."
- A rejected submission (`POST /admin/kyc/:id/reject`, `{ reason }`) can be resubmitted (`POST /kyc/resubmit`) — this creates a fresh submission (`attemptNumber` increments), it doesn't edit the rejected one. Only one submission can be `pending_review` at a time per business (`409 KYC_ALREADY_PENDING` on a second attempt while one's already in the queue).
- A previously-`verified` business can be pulled back to `revoked` by an admin (`POST /admin/brands/:brandId/kyc/revoke`) if fraud is discovered after approval — this immediately re-gates project posting/quoting for that business, same as if they'd never been verified.
- `Brand.kycStatus` (`"not_submitted" | "pending_review" | "verified" | "rejected" | "revoked"`) is what every KYC-gate check reads — surface it directly rather than trying to infer status from a `GET /kyc/me` submission history read.

## B2B marketplace: 1 free quotation, then a paid account-wide unlock

- A KYC-verified business posts a `Project` (a contract/RFP); other KYC-verified businesses submit `Quotation`s against it — quoting requires the same verification as posting, not a lighter bar.
- The project's poster sees exactly **one** quotation for free (the earliest submitted) — every additional quotation is paywalled. Unlocking is **not** a per-project purchase and there is **no "Basic"/"Premium" business plan** (that vocabulary is reserved for per-ad-campaign tiers, `Config: campaign.tiers`, and has nothing to do with this feature). Instead: `POST /quotation-unlock/purchase` buys a flat-rate (`Config: quotationUnlock.priceNgn`, default ₦5,000), account-wide, time-boxed pass (`Config: quotationUnlock.durationDays`, default 30 days) that reveals every quotation on **every** project the business posts while it's active.
- The unlock purchase is a **wallet debit** — a business must fund its wallet first via `POST /wallet/topup/initialize`/`verify` (see `API_GUIDE.md`'s "Wallet top-up" section) before it has a balance to spend. `402 INSUFFICIENT_BALANCE` on the purchase attempt means "prompt a top-up," not a generic error.
- Buying an unlock pass while one is still active **extends the existing expiry**, it doesn't reset to a fresh 30 days from the purchase moment — a business renewing early never loses days it already paid for.
- If the specific quotation that was the poster's free look gets withdrawn by its submitter, the free slot automatically re-points to the next-earliest still-live quotation (if any) — the poster never loses their one free look just because a vendor changed their mind.
- A quotation's amount can't be edited after submission — the submitting business withdraws (`POST /quotations/:id/withdraw`) and resubmits fresh if they want to change their number.

## Contact & ratings: message only what you can already see, rate only who you've contacted

- A private contact thread (`POST /business-contact/threads`) can only be opened on a quotation the poster is currently allowed to see — the free one, or any quotation while an unlock pass is active. Trying to open one on a quotation that's still paywalled returns `403 QUOTATION_NOT_VISIBLE`. This is the actual privacy boundary the pay-to-unlock model depends on: a locked quotation's contents (and the ability to reach whoever submitted it) stay hidden together.
- Rating (`POST /business-ratings`) requires an existing contact thread between the rater and the business being rated, on that specific project — `403 CONTACT_REQUIRED` otherwise. **There is no separate "mark this project completed" step in v1** — contact having happened is the entire trust bar for being allowed to rate. Don't build an award/completion flow; it doesn't exist yet.
- A business can rate the same counterpart again on a **different** project — the once-only rule is scoped to `(project, rater, rated)`, not to the pair of businesses forever. Two businesses that work together repeatedly can rate each independent engagement.
- False-review moderation is reactive, the same posture as ad-campaign moderation: `POST /business-ratings/:id/report` is idempotent per reporter (a repeat report is a silent no-op), enough reports within `Config: businessRating.autoFlagWindowMinutes` (default 60) crossing `Config: businessRating.autoFlagReportThreshold` (default 3) surfaces the rating on `GET /admin/business-ratings/moderation/flags` — **never auto-hides it**. Only an explicit `POST /admin/business-ratings/:id/hide` removes a rating from public view, and it's never deleted, just excluded from `GET /business-ratings/business/:brandId`'s public reads.

## Forum: flag → admin review → resolve, and a one-way winner-share bonus

- Anyone signed in can post threads/posts; there's no pre-publish moderation queue here either, same reactive posture as everything else in this API. A `locked` thread (admin-controlled) rejects new posts with a `400`, but existing content stays readable.
- Liking a post (`POST /forum/posts/:id/like`) is idempotent, **not a toggle** — liking an already-liked post returns `{ liked: false }` as a normal `200`, not an error; it just means nothing changed. Unliking (`DELETE /forum/posts/:id/like`) is the separate, explicit way to remove a like, and returns `{ unliked: false }` if there was nothing to remove. Don't build a single "like button" that assumes calling the like endpoint twice toggles state — it doesn't.
- Flagging a post (`POST /forum/posts/:id/flag`, `{ reason }`) has **no per-user dedup** — unlike ad-campaign reports or business-rating reports elsewhere in this API, the same user can flag the same post more than once, each a separate row. Don't build UI that assumes "you already flagged this" is a state the backend tracks or blocks.
- Admin review (`GET /forum/moderation/flags?status=open`, `PATCH /forum/moderation/flags/:id { status: "resolved"|"dismissed", hidePost? }`) is manual, one flag at a time. Resolving with `hidePost: true` sets the underlying post's `moderationStatus` to `"hidden"` — **not** `"removed"`. `GET /forum/threads/:id/posts` only excludes `"removed"` posts from its results; a `"hidden"` post still comes back in the list. If the product wants hidden posts to actually disappear from a normal thread view, that filtering has to happen client-side (or ask backend to add it) — right now, "hidden" is a moderation-side flag on the record, not a public-visibility gate.
- Winner-share submissions (`POST /forum/winner-submissions`) are a self-report — a viewer claims they shared a win publicly and links to the post; `claimedLikeCount` is exactly that, self-reported and never independently verified by the system. Admin verification (`POST /forum/winner-submissions/:id/verify`) credits a flat, Config-driven points bonus (`Config: forum.winnerShareBonusPoints`, default 5) — **verifying an already-verified submission is a silent no-op**, it never re-credits, so it's safe to build a retry-safe "Verify" button. Status transitions are **one-way once resolved**: a `"rejected"` submission can never later be verified, and a `"verified"` one can never later be rejected — don't build an admin UI that lets either be re-decided.
